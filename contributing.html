Contributing

OCF intends to be shaped by its contributors. Participation could include technical research, software adaptation, documentation, testing and the organisational work needed to make those activities sustainable. This page describes possible work; it does not announce an established contribution programme.

Current participation information

No repository, email address, discussion channel or submission procedure has been supplied for publication. Consequently, this site does not provide a contribution destination or ask you to register. Verified channels and project-specific guidance would need to be published before contributions can be submitted through an OCF process.

Technical research and standards analysis

Future participants could analyse browser capabilities, map platform dependencies and compare architectural approaches. Useful research would separate specification guarantees from observed browser behaviour and record version-specific limitations.

A focused investigation might ask whether one document conversion can run locally, what blocks a game’s networking model, or which storage operations a particular workflow needs. A small, reproducible result is more useful than an unsupported assertion of broad compatibility.

Software porting and implementation

Potential work includes isolating portable application logic, adapting runtime imports, developing browser interfaces and replacing platform-specific dependencies. Any implementation should begin with a rights review and a defined task, with clear tests for correctness and known exclusions.

Changes that can be maintained with upstream software are preferable to unexplained forks. New contributors should not be expected to commit to maintaining an entire application before the scope and dependencies are understood.

Compatibility testing and accessibility

Testing could cover browser engines, operating systems, devices, input methods and assistive technologies. Reports should identify exact versions and reproducible steps, include expected and actual outcomes, and distinguish a failure to launch from a failure in a particular task.

Testing data import, saving, export and interrupted sessions is as important as checking visual output. Private documents, account credentials and proprietary assets should not be placed in public test reports.

Documentation and preservation

Contributors could explain architecture, maintain dependency inventories, clarify licence requirements and improve instructions for reproducing experiments. Preservation-oriented work could document file formats, lawful runtime requirements and ways to recover user data from unsupported environments.

Documentation should make uncertainty visible. A proposed technique, a working experiment and a supported release require different language. No research publications or completed ports are being claimed by listing these possibilities.

Shaping the organisation

Contributor leadership should include people doing documentation, testing and review as well as implementation. Future processes would need clear expectations for attribution, decision-making, disagreement and stewardship of shared work.

The principles describe this intended approach. The proposed objectives and research overview provide context for identifying useful, bounded work once verified participation channels are available.
