Ubiquity

Ubiquity is the codename of the central technical research and development project within The Web Independence Initiative. It seeks to investigate how an extensive range of existing digital technologies could operate through standards-based web technologies. The architectures below are proposed directions, not implemented OCF components.

Applications, utilities and specialised software

For desktop applications, the useful unit of compatibility is often a workflow: opening a document, editing it, running a calculation and exporting a result. Porting a computation library can be more tractable than reproducing the whole application. Native menus, window management, clipboard integration, printing and filesystem assumptions would need separate treatment.

Mobile software can assume touch gestures, background execution, notifications and sensors. A browser adaptation would need to account for permissions, page lifecycle restrictions and devices without equivalent hardware. Interface changes should preserve useful functionality without assuming that every native capability has a browser equivalent.

Utilities such as format converters, text processors and archive tools may fit local, bounded execution. Specialised engineering, scientific or media software can require large datasets, numerical reproducibility, licensed libraries or attached instruments. Its suitability would depend on resource limits and the consequences of errors, not merely whether a compiler accepts the code.

Games and interactive environments

Game adaptation involves the engine, content assets and services as well as executable code. Rendering may require a different graphics backend or shader translation. Frame pacing, GPU memory, texture formats and download sizes affect practical performance. Web audio must account for user activation and timing; keyboard, pointer, touch and gamepad controls require appropriate mappings.

Save data needs reliable storage and explicit export. Multiplayer protocols may depend on transports unavailable to ordinary browser pages, or on authentication and matchmaking services controlled by third parties. Network adaptation requires authorised service changes or gateways, with their own operational costs and security responsibilities.

Kernel-level anti-cheat, proprietary platform integration and unavailable servers can block compatibility. The project is not intended to bypass anti-cheat, digital rights management or ownership checks. A playable local demonstration would not establish full multiplayer or content compatibility.

Direct source-level porting

Where source and licence permissions permit, developers could modify a program to target browser execution. The work includes replacing platform calls, revising blocking loops to cooperate with event-driven execution, adapting dependencies and designing a browser interface. A portable core with a well-separated interface is a plausible starting point.

This approach can preserve substantial application logic, but it requires maintainable changes and cooperation with upstream development where possible. A port that compiles can still differ in file handling, timing, text rendering or numerical results.

WebAssembly-based execution

WebAssembly provides a portable execution format that can be a compilation target for suitable code. It can support computational cores and existing language toolchains, while JavaScript and browser APIs provide host integration. It is not an automatic translator for arbitrary desktop binaries and does not supply an operating system’s services.

A proposed port must supply or adapt the imports its module needs, handle asynchronous browser operations and account for memory and threading constraints. See the WebAssembly portability documentation for the distinction between portable execution and host APIs.

Compatibility and abstraction layers

A compatibility layer could implement a defined subset of an existing interface on top of browser capabilities. An abstraction layer could let application code select native or web backends for storage, graphics or input. Neither approach guarantees that undocumented behaviours or privileged operations can be reproduced.

Potential shared infrastructure might include filesystem adapters, input mappings and test fixtures. These are candidates for investigation, not available Ubiquity services. Any shared layer would need precise scope, observable failure modes and a clear account of unsupported operations.

Emulation where appropriate and lawful

An emulator can reproduce aspects of a processor or machine so that software runs in a model of its original environment. This may be useful for older programs with no maintainable source, but it can add execution overhead and require careful timing and peripheral modelling.

The emulator, firmware, operating-system image, application and content can have separate rights and distribution conditions. Access to one does not authorise redistribution of the others. Preservation work must document lawful inputs and avoid treating technical feasibility as legal permission.

Reimplementation using web standards

A web-specific implementation could reproduce a documented format, protocol or useful workflow without retaining the original program’s execution model. Semantic HTML, browser APIs and accessible interaction patterns can offer a better fit than recreating a complete desktop environment.

Reimplementation carries its own correctness risks. File-format edge cases, language semantics and undocumented behaviours may matter to users. It should be evaluated against independent fixtures and clearly distinguish compatible features from deliberate changes. Rights to code, assets and specifications must be considered separately.

Interfaces and platform dependencies

Interface adaptation includes keyboard operation, focus order, responsive layout, assistive-technology support and alternatives to pointer-only controls. Rendering a native interface into a canvas does not automatically expose its controls to accessibility tools. Interaction design is therefore part of compatibility engineering.

Platform-specific dependencies may need replacement rather than imitation. A file picker and export mechanism can replace assumptions about unrestricted disk access. Browser storage could represent a working directory, but it is not the user’s whole filesystem. Drivers, system services, process control and privileged extensions may have no suitable browser replacement.

Existing runtimes and proposed infrastructure

Software may depend on a managed runtime, interpreter, plug-in interface or embedded scripting language. A runtime port could allow multiple programs to share execution support, but its standard library, native extensions, package loading and security model would also need review. A working interpreter does not establish compatibility for its entire ecosystem.

A useful future architecture might separate execution, host services, user interface, data exchange and compatibility tests. Its suitability should be demonstrated with small experiments before any framework is treated as general-purpose. Deployment requirements and server dependencies should be recorded explicitly.

Limitations and unresolved questions

  • Which workflows offer useful results with realistic browser memory, download and execution costs?
  • How can results be compared across browser engines, devices and program versions without overstating support?
  • Which filesystem, threading and networking assumptions can be adapted without changing essential behaviour?
  • How can offline use, data export and recovery be verified under quota limits and interrupted sessions?
  • Which abstractions remain useful across applications without hiding critical incompatibilities?
  • What maintenance burden follows from upstream changes, evolving browser APIs and security updates?

Hardware dependencies, proprietary services, licensing restrictions, anti-cheat and operating-system-specific functionality remain possible blockers. See research areas and methods and proposed objectives for how these questions could be investigated.
