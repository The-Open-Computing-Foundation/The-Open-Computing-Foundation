The Web Independence Initiative

The Web Independence Initiative (WII) is OCF’s principal undertaking. Its long-term objective is to make practically everything in computing accessible, compatible with, and wherever feasible native to the web. Ubiquity is the codename of its central technical research and development project.

The problem of platform dependence

A program may require a particular processor architecture, operating-system interface, graphics driver, installation system or proprietary runtime. Users can possess legitimate copies and still lose practical access when those dependencies are no longer available. Mobile distribution restrictions and device-specific interfaces can impose additional barriers.

Traditional distribution delivers a package for an assumed environment. Installation may modify a system, place files in privileged locations or depend on background services. Merely downloading that package through a website does not change its execution requirements. The initiative asks which dependencies are essential and which can be replaced or abstracted.

What web compatibility means

Compatibility is a set of observable behaviours, not a single yes-or-no label. A program might launch but fail to open a document, save a result, render correctly or accept accessible input. A credible assessment needs to identify the version, workload, browser, operating system, hardware and known failures.

Web compatibility may involve compiling source for a browser runtime, substituting browser APIs for platform APIs, translating data formats or reproducing a necessary execution environment. Each approach preserves different parts of the original program. Successful adaptation should be assessed against the tasks users need to perform.

Web access and web-native execution

Web access means a browser provides a route to an experience. A remote desktop or streamed game satisfies that description while the original application runs on a server. It can be useful, but it retains server capacity, network latency and service continuity dependencies.

Web-native execution means the application is implemented around web execution and interaction models. Substantial computation can run on the user’s device through JavaScript or WebAssembly, with browser-managed graphics, input and storage. Web-native applications may still use network services; the term does not guarantee offline operation, decentralisation or privacy.

The initiative would distinguish local execution, remote execution and hybrid designs explicitly. An embedded remote interface should not be described as a native port.

Proposed scope

  • Applications: investigate desktop and mobile workflows, document formats, interface adaptation and runtime dependencies.
  • Games: examine graphics, simulation, audio, controls, saved progress and multiplayer services.
  • Utilities and specialised software: evaluate parsers, converters, engineering tools and workflows with unusual resource or hardware requirements.
  • Legacy environments: consider lawful emulation and adaptation where original systems are difficult to maintain.
  • Interoperability: examine shared formats, protocols, interfaces and conversion processes across ecosystems.

These categories define possible research, not a list of supported software. Feasibility would be determined per program and per workflow. Direct device control, kernel integration, proprietary services and strict real-time requirements can make some uses unsuitable.

Interoperability and user control

A browser implementation offers limited independence if its data can only be read by one service. Interoperability research must cover import and export, documented file formats, protocol behaviour, text encodings and predictable error handling. Conversion should make losses visible, including unsupported metadata or features.

Shared interfaces could allow different implementations to use the same compatibility components. Such interfaces would need clear versioning and tests; premature generalisation could instead entrench incorrect assumptions about software behaviour.

Relationship with Ubiquity

WII sets the mission and scope. Ubiquity names the central project through which technical approaches could be investigated and developed. The research overview describes relevant capabilities and questions, while the proposed objectives describe an evidence-led progression.

This site presents objectives and proposed research directions. It does not announce a completed compatibility engine, deployed infrastructure, software ports or published experimental findings.

Boundaries and long-term vision

Universal browser execution is not promised. Anti-cheat systems, digital rights management, licence conditions, unavailable source code, abandoned services and hardware dependencies may prevent a legitimate adaptation. Performance, memory and battery constraints can also make a technically possible port impractical.

The long-term vision is a web that supports a much wider range of useful computing, with fewer arbitrary platform barriers. Progress would mean documented, reproducible improvements in particular tasks, achieved while preserving user choice, security and respect for software authors.
