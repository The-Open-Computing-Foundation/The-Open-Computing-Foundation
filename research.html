Research

This page outlines proposed research for The Web Independence Initiative and Ubiquity. The linked specifications describe external web technologies; they are not OCF publications or evidence of completed OCF experiments. Feature availability must be tested in the intended browsers and devices.

Browser execution and concurrency

JavaScript and WebAssembly offer different routes to browser execution. Research would examine toolchain assumptions, module loading, host interfaces and the cost of crossing execution boundaries. Existing native code may rely on process creation, unrestricted files or synchronous system calls that require redesign.

Web Workers in the HTML Standard describe execution away from the main interface thread. Workers can support responsiveness but cannot directly manipulate the document. Shared-memory designs introduce synchronisation and deployment requirements; parallelism is not a substitute for a measured workload model.

Graphics and audio

WebGPU defines GPU rendering and computation interfaces. Research would need to evaluate device limits, shader translation, fallback behaviour and differences between the original graphics API and browser execution. WebGL specifications provide another graphics route, with a different programming model.

Graphics support alone does not establish engine compatibility. Resource formats, synchronisation and memory pressure matter. Audio work would examine scheduling, user activation, device changes and synchronisation with rendering; the Web Audio API is a relevant reference.

Storage, files and offline operation

IndexedDB provides structured browser storage, while the Storage Standard describes the broader storage model. Research would need to examine quotas, eviction, transactions and recovery after interruption. Browser-managed data should not be treated as a guaranteed permanent archive.

A proposed filesystem adapter should distinguish application working storage from explicit user-selected files. Import, export and backup are essential compatibility tasks. Offline capability also requires that executable code and necessary resources remain available; it cannot be inferred from the presence of local storage.

Service workers can mediate requests and support caching in an appropriate secure context. They have lifecycle limits and do not provide an always-running system service. This informational website does not install a service worker.

Input and accessibility

Research would compare keyboard, pointer, touch and gamepad behaviour with original application assumptions. Pointer lock, fullscreen and device access have permission or activation constraints. A workflow designed for precise mouse input may need a different interaction model on a small touch device.

Access across platforms must include access for disabled users. Semantic controls, visible focus, text alternatives, zoom and screen-reader behaviour should be tested alongside execution. WCAG 2.2 offers a reference for accessibility evaluation; a standards reference alone does not establish conformance.

Networking and service dependencies

Ordinary browser pages do not provide unrestricted raw TCP or UDP sockets. HTTP, WebSockets and WebRTC offer different communication models, each with constraints. An existing service protocol may require changes or an authorised intermediary.

Proposed studies should identify authentication, matchmaking, update and content-delivery dependencies. A gateway can restore a communication path while adding a new availability and trust dependency. Service shutdown, latency and interrupted connectivity should be assessed rather than hidden behind a successful connection test.

Security and privacy

The browser sandbox limits what software can do to a user’s system. A compatibility design should work within that boundary. Untrusted documents, downloaded programs and emulated environments still require careful input handling, origin separation and resource limits.

Permission prompts should correspond to necessary capabilities, with failure handled safely. Cross-origin rules and secure-context requirements can affect architecture. Data processing should stay local where practical, and any server transfer should be documented. Independence must not require weakening browser security.

Performance and reproducibility

Evaluation should distinguish startup, download, compilation, steady-state execution, responsiveness, memory use and energy cost. A small demonstration cannot establish performance for large projects or long sessions. Thermal throttling and background-tab policies can change results on portable devices.

A proposed test record should state software and asset versions, browser and OS versions, hardware, feature flags, test inputs and expected outputs. Results should include failures and a reproducible procedure. Comparative measurements need equivalent workloads and stated uncertainty; no OCF benchmark results are claimed here.

Interoperability and compatibility assessment

Research would cover encodings, file formats, numerical behaviour, error handling and version negotiation. Round-trip tests can reveal loss during import and export, but independent reference files are also needed because two implementations can share the same mistake.

Proposed evidence categories
CategoryWhat to record
ExecutionWhether the program starts, completes a defined task and produces correct output.
InteractionInput coverage, accessible operation and behaviour at different viewport sizes.
DataImport fidelity, persistence, export, recovery and documented losses.
DependenciesRequired services, permissions, licences and unavailable platform features.
Practical limitsPerformance, memory, device coverage and known failures.

Compatibility reports should identify tested cases rather than certify an entire software category. The proposed objectives describe how such methods could be developed.
